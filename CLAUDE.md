## What this is

Single-page marketing site for **Proovd** (Next.js 16 App Router + TypeScript, Turbopack). One route: [app/page.tsx](app/page.tsx) renders `IntroGate`, then `<main>` composing the sections in order (Hero, Navbar, Evan, Creators, Risk, Days, Guides, Pricing, FAQ) with `HoverFX` last — most sections are one viewport tall; Evan is a multi-viewport scroll story. `three` (Evan's corner-peel) is the only runtime dependency beyond React/Next, and it's dynamically imported.

**[components/intro-gate.tsx](components/intro-gate.tsx) owns the first ~4.5s of the page** — a full-screen `z-index: 1000` intro that runs, then lifts. One `data-phase` state machine drives it: `loading → choosing → picked → sealing → playing → done → gone`. All choreography is CSS keyed off that attribute; the component only advances the phase and drives the `<video>`s.

- **Loading** → before the buttons (owner): a count under `crank-load.mp4` looping above it (~750 KB, same no-src/`preload="none"` discipline as the stinger, gated on Save-Data/tablet/codec — its absence just hides the clip, the count runs regardless). **The count is REAL** (owner: "the loader should not be finished before everything else is loaded"): rAF writes `textContent` up to **90%** over `LOAD_MIN_MS 1500`, HOLDS there until the assets are actually in — window `load`, the crank's `loadeddata`, the stinger's `canplaythrough` — then runs 90→100 over `LOAD_DONE_MS 320` and the tiles come up after `LOAD_TAIL 250`. Every wait resolves on its own error path too, and the whole set is raced against `LOAD_MAX_MS 8000`, so a dead asset costs the cap at worst; a warm cache still spends 45% of the floor so the count can't flash 0→100. The first shipped version was a fixed 1.8s count and **that is why the crank never appeared live** — 1.8s outran its own 768 KB fetch, so the tiles arrived before the first frame did. `.loader` and `.choices` share grid cell `1/1`; the tiles hold layout underneath at `visibility: hidden` so the swap is an in-place reveal. Reduced motion skips straight to `choosing`. The StrictMode-unmount claim-release now covers `loading` OR `choosing` — `finishIntro()` from there would settle the intro for good and the remount would land on `gone`. **Phone drops the tile texture entirely** (owner) — `.tile::before` is `display: none` ≤700px, and `layout.tsx`'s preload for `btn texture.png` is `media="(min-width: 701px)"` so phones don't fetch the 135 KB either; change one, change both.
- **Pick** → the tile strobes 3 × 0.12s while the other shuts (`max-width`/padding/border → 0, its grid row `1fr → 0fr`, row-gap → 0, so the survivor glides to centre). The row collapse is the flexible-track trick `faq-section.module.css` uses to open an answer, run in reverse.
- **Sealing** → the picked tile takes that identical exit, one beat later.
- **Playing** → a muted 0.97s stinger (`public/assets/desktop-video.mp4`, ~560 KB after the owner's re-encode), `object-fit: cover`.
- **Done/gone** → the clip is cut away onto its own snapshotted last frame, and `<Hero />` runs its normal reveal.

Rules that are load-bearing here — breaking any of them re-opens a bug that was already found and fixed:

- **`go()` is monotonic.** `finishIntro()` can fire from *outside* the sequence (Escape, the module deadline), which leaves the pick chain queued. A later `go("sealing")` would drag the opaque overlay back over a revealed hero with nothing left to remove it — the `whenIntroDone()` handler runs exactly once. That handler therefore also tears the sequence down (`ended`, `clearTimers`, `detachVideo`) *before* advancing, and the exit timer is deliberately kept out of the array `finish()` clears.
- **The hero backdrop is the clip's own last frame.** On the desktop clip path `snapshotFrame()` draws the `<video>` into a `<canvas>` and puts it in `.bg` — pixel-identical by construction, so there is nothing to keep in sync and no separate still is fetched at all. Measured: ~1–4 ms, canvas is not tainted (same-origin file). **Do not encode it first** — `toBlob('image/webp')` on a 1080p frame measured 414 ms of main-thread work here, for a `<canvas>` that was already paintable. A held frame costs about the same GPU memory as the decoded still it replaces (~8 MB either way), so this is a straight saving of the still's bytes.
- **There is NO fallback still any more.** The owner deleted the hero art outright in the webp sweep (`new_hero_desktop.*` and `Hero_mobile.webp` are gone; `HERO_ART` was removed with them and `loadStill()` is a kept-for-sequencing no-op). On every path where no clip frame can exist — reduced motion, Save-Data, refused autoplay, unplayable codec, dead file, JS off — the hero stands on `.hero`'s own `background-color` surface, and the gate always *dissolves* there: `heroDecodedRef` can only be set by a real snapshot now, so `data-cut="hard"` is unreachable without a frame.
- **`data-cut="hard"` requires all three of**: a frame painted, `heroDecodedRef` (else the cut lands on `.hero`'s green `background-color` against the navy — a colour flash), and `cutOnEndedRef` (the `timeupdate` net can fire 60ms early, and the final frames are where residual motion lives). Anything less dissolves.
- **`.video` is sized from `--crop-w/h/y`**, published by a `ResizeObserver` on `section[aria-label="Proovd"]`. `cover` resolves against the box it paints into, and `.hero` is `min-height: 100svh` — taller than the viewport when content overflows — so a viewport-sized clip would zoom/shift at the cut instead of matching.
- **The clip is gated on `saveData` only, never `effectiveType`.** That was measured misfiring: Chrome reports `2g`/`slow-2g` while its estimate is cold, denying the clip on localhost. Slow connections are handled by the measured `T.buffer` grace instead.
- **[lib/intro.ts](lib/intro.ts) exposes TWO signals, and conflating them is a bug that has already happened once.** `whenIntroDone()` = "the hero may un-park"; `whenIntroDismissed()` = "the gate may leave". The idle backstop resolves only the first. When the gate hid itself off the *same* promise, it evaporated on its own ~15s after load in front of anyone still reading the two options, so their click landed on nothing — which presents as "the second tile doesn't work". Only a real end (clip finished, genuine failure, Escape, post-pick deadline, unmount mid-sequence) may dismiss the gate. `introSettled()` reports *dismissed*, not *settled*, for the same reason.
- **[lib/intro.ts](lib/intro.ts) is the handoff** — promises that can only resolve. It owns every backstop so no consumer can forget one: a claim grace (gate present but silent), a 7s sequence deadline (armed by the pick), and a 15s **idle** backstop for "nobody ever clicks", which the pick *cancels* — otherwise a visitor who reads the options slowly would have their hero reveal spent behind the still-opaque gate. `whenIntroDone()` also answers "is there even a gate?" via the server-rendered `data-intro-gate` marker, so deleting `<IntroGate />` from `page.tsx` resolves it instantly rather than parking the hero on a timer.
- **The statement photo swaps main→smiling by stacking, not `src`.** Two `<img>` (`[data-ev-photo]` + `[data-ev-photo-smiling]`) sit absolutely inside `.photoMask`, smiling pre-decoded at `opacity:0`; the cut flips its opacity to 1. Re-setting `src` on a live `<img>` flashes during decode/repaint even when cached — that was the "pic flickers" bug. On phone the photo window GROWS in layout and holds big (see the Evan notes below); desktop keeps the straight settle-then-smile. At the handoff the photo fades up-and-out with the words on BOTH postures — there is no kicker avatar anywhere any more, so the old `flyToAvatar` flight is gone.
- **`history.scrollRestoration = "manual"`** (set in IntroGate) + `scrollTo(0,0)`: every load starts at the top, never the restored position. The hero→Evan scroll-jack assumes you begin on the hero, and a reload landing mid-page fought it.
- Reduced motion skips the video entirely and lands straight on the hero. `<noscript>` + `@media (scripting: none)` hide the gate outright — with JS off it is a modal with no way out.

The pick is still sticky and navigates nowhere (`TODO(destination)`); both tiles run the same intro. It **is** load-bearing in one way, though: the gate records it via `setIntroChoice()`, and the Evan story reads it through `getIntroChoice()` once the intro resolves, to decide whether to tell `IDEA_STEPS` or `PRODUCT_STEPS`. Evan used to carry its own fixed segmented toggle asking the identical question with the identical two labels — that's gone, so the gate is now the only place the question is asked and `PRODUCT_STEPS` is reachable only through it. Nobody choosing (idle backstop, reduced motion, no gate) leaves the story on `idea`.

Deployed as a Docker standalone image (multi-stage `node:22-alpine`, non-root) via Dokploy on push to `main` (see DEPLOY.md). Config is env-driven and **inlined at build time** — Dokploy passes each value as a build arg (`Dockerfile` ARG/ENV pairs), so a var set only at runtime has no effect. The set: `NEXT_PUBLIC_SITE_URL` (canonical origin; code falls back to `https://proovd.co`), `NEXT_PUBLIC_CLARITY_PROJECT_ID`, `NEXT_PUBLIC_UMAMI_SRC` + `NEXT_PUBLIC_UMAMI_WEBSITE_ID`, and `GOOGLE_SITE_VERIFICATION` (the one non-`NEXT_PUBLIC_` var, read server-side in the metadata). All optional — each feature stays off until its var is present.

## Design system — three layers

1. **Decision layer:** `docs/design-system/Proovd DNA.md` — the brand/UX/motion spec. The `§` numbers in code comments (e.g. "§6.4") refer to its sections. Read it before building or restyling any UI; it contains hard rules (color pairings, "nothing teleports", fail-loud font/motion checks, no shadows/gradients, sharp radii). Its GSAP-only motion rule (§6, §6.7) is deliberately overridden in this codebase — see Motion below.
2. **Value layer:** [styles/proovd.css](styles/proovd.css) — tokens, section modes, element identity, and the Satoshi `@font-face`. **Never edit or format this file** (it's excluded from Biome); it is replaced wholesale from `docs/design-system/proovd.css`, which is currently byte-identical. The intended contract: components pick a section mode class (`.mode-none` / `.mode-dark` / `.mode-light` / `.mode-drawer`) and read semantic slot vars (`--mode-title`, `--mode-body`, `--btn1-*`, …) rather than hex. In practice these landing sections read the raw **token vars** directly (`--brand`, `--dark`, `--sp-*`, `--fs-*`) — the `.mode-*` slot system and the `.btn`/`.card`/`.sticker` element classes are essentially unused here — and a few section-local palettes are hardcoded (the creator card sheet in `creators-section.tsx`, the `#011E0B` shared by navbar/risk/days/Evan-product-mode). So don't expect to find `.mode-dark` on a section; look for the token vars in its `*.module.css`.
3. **Component layer:** CSS Modules co-located with each component (`components/*.module.css`). No Tailwind, no CSS-in-JS, no UI libraries. [styles/globals.css](styles/globals.css) holds only page-level overrides (hidden scrollbars, the `data-hover="underline"` ::after scaffolding).

Fonts: Satoshi is load-bearing, self-hosted in `styles/fonts/`. `app/layout.tsx` imports the woff2 for its hashed URL (ambient decl in `types/assets.d.ts`) and `preload()`s it so the preload always matches the `@font-face` request. The DNA's fail-loud `document.fonts.check` notice (§3) is **not** implemented.

## Motion & scroll architecture

- **Scroll is written in exactly two shapes; nothing else anywhere writes it.** (1) The Evan section's own machinery (the hero jack, the magnet, its statement hold). (2) `holdScroll` in [lib/motion.ts](lib/motion.ts) — the shared **arrival lock** every transition-owning section uses (creators' spin, risk's doors, days' pinhole, the guides jack): it pins `<body>` immediately, glides `body.style.top` onto the section's own top (forward only — arriving from below holds in place), fires `onSettled` at the landing, and releases on its `ms` backstop or its returned release fn, which every caller runs on unmount. **Two rules came out of the first live phone build.** (1) When it stands down because the body is already pinned, it now **waits (rAF-polls) for the page to be free before cueing** — firing `onSettled` immediately was a real bug: the other section's glide is still moving `body.top`, which moves every rect, which trips the waiting section's own IntersectionObserver a viewport early, so its entrance played off-screen mid-flight and was over before the reader arrived ("the sections on the phone glitch so bad"). It still always cues, so a collision costs a hold, never an opening. (2) **Each glide frame dispatches a synthetic `scroll` event** — a pinned body emits none, so every passive `scroll` listener on the page goes blind for the whole hold and snaps on release, which is what the navbar was doing ("the nav bar glitches", "takes a bit to go away"). Every such listener here reads position through rects or the `-body.top` convention, both correct mid-hold; they just need telling. **Trigger depth is posture-split for all three arrivals** (risk/days/guides: 45 on phone vs 85/90/72 on desktop) because `gap` — and therefore the length of the un-fingered auto-glide — *is* the trigger line: 0.85 of a phone viewport is ~690px of page moving on its own ("the sections kind of scroll up alone"), while 45 lands a ~365px carry on a section already filling over half the screen, and keeps the line clear of the seam where a URL-bar collapse/expand (a resize, so it moves the observer's line with no gesture behind it) could otherwise walk a resting section across it. No CSS scroll-snap. Everything else reads position passively (rAF-queued passive listeners) and never writes it.
- **Hero → Evan is scroll-jacked (the only jack on the site).** The first downward scroll/swipe while you're still on the hero (`root.top > 50vh`, body not locked) calls `beginIntro()`, which glides the full distance to the Evan top via `settleToTop()` and plays the statement there — you don't hand-scroll to it. It fires once, then removes its own wheel/touchstart/touchmove listeners; everything below Evan is native. `beginIntro()` is shared with the `onceInView(70%)` fallback (for when the jack window was skipped), guarded by `introStarted` so only one wins.
- **The intro snap + hold.** When the story is SCROLLED into view, `holdInput()` swallows wheel/touchmove — so the statement screen and every section under it is neither scrollable nor swipeable while it plays — and `settleToTop()` glides the page onto the section top. Two rules are load-bearing:
  - **The lock engages synchronously** the instant the section crosses the 70% line, *before* the `document.fonts.ready` wait, not inside its `.then()`. Deferring it left a gap a continuous scroll slipped through.
  - **The lock is `position: fixed` on `<body>`, because nothing lighter stops an iOS momentum fling.** preventDefault-on-touchmove and `touch-action: none` both failed on phone: once the finger lifts no touchmove fires, and touch-action only governs the *next* gesture — so the fling that triggered the intro carried the page past. `holdInput()` pins the body (`position:fixed; top:-scrollY; width:100%`) + `overscroll-behavior:none` on `<html>`; a pinned body has no scroll range, so in-flight momentum has nothing to move. **The settle glide animates `body.style.top`** (not `scrollTo`, which does nothing while pinned): `lockedY` is the virtual scroll, `body.top === -lockedY`. `releaseHold()` clears the pin and `scrollTo(0, lockedY)` in the *same synchronous tick* (coalesced into one paint, so the scrollY-0 intermediate never shows — no jump), then pings `updateRef.current()` so E1 re-syncs. **A body left `position:fixed` freezes the entire site**, so: every exit path (cut, throw, cleanup/unmount, StrictMode) routes through `releaseHold`, and a catastrophe net at E4 mount (before the reduced-motion bail) clears any leaked pin and restores the offset parsed from `body.top`. This cleanup is the most load-bearing code in the section.
  - The fling-past skip catches down to `-0.9vh` (was `-0.5vh`): on phone a swipe's momentum can outrun the async observer, so a tighter bound let it engage too late / not at all.
  - **It only fires when the user SCROLLED in**, gated on `window.scrollY` having moved from `mountScrollY`. If the page LOADED already sitting in the section (reload, deep link, scroll restoration), `onceInView` fires immediately on mount with scrollY unmoved → skip, just show the story. Locking and gliding a visitor who never scrolled was "it drags me on reload".
  - Released on cut/throw/cancel/unmount; the glide aborts the moment the hold releases so it never chases a freed user.
- **The whisper magnet.** After a scroll or swipe settles, it tidies onto the nearest step. Its trigger rules are load-bearing — getting them wrong reads as the page moving on its own:
  - **Armed ONLY by `wheel` and `touchmove`** — a deliberate scroll or swipe. It is emphatically **not** armed by the `scroll` event. That was the original bug: `scroll` fires for every movement including the magnet's own nudges, resizes, anchor jumps and scroll restoration, so it re-armed itself and fired with no gesture behind it. `keydown`/`pointerdown` only retire the intro boost; they never arm it.
  - **No idle timer.** The old "far rescue" fired up to 2s after you had stopped, which is what read as unprompted movement. It now waits `SETTLE_MS` after the last gesture *and* the last moved pixel (polling position, so a touch fling's momentum finishes first), then snaps once.
  - **No viewport-size gate.** Screen size can neither trigger nor suppress it. An earlier `MAGNET_MIN_VH` threshold was the wrong fix and is gone.
  - Any new gesture cancels an in-flight nudge, and an external scroll mid-nudge aborts it, so it can never fight the user. `engaged()` keeps it inside the story — gesturing on the hero or the FAQ does nothing (verified).
  - **The ends differ by posture and by explicit owner request.** The bottom **scroll-jacks the seam into creators on BOTH postures** (owner: "scrolljack from the section before it to this one", then "I want this section to scroll jack from before it going to this" for the laptop) — a DOWNWARD run (`segDir === 1`; direction-gated because `best < 0` also holds when an upward gesture from creators lands short of the pledge beat, and jacking there would move against the user) glides the page onto `#creators`' top (`best = nextRect.top`, advance ramp), where the creators entrance trigger (`onceInView(70)` on phone, the pin on desktop) starts its intro spin mid-glide and the entrance's own `holdScroll()` freezes the page the moment that glide goes still. Desktop no longer has a free downward exit here. **The seam is tested FIRST, before `engaged()`, off the section's own bottom edge** — and that placement is the whole reason it works on desktop. Inside `engaged()` the jack is unreachable in practice there: measured at 1440×900, once the magnet has snapped the pledge stack onto the reading line only **442px** of section remain below it, so a single trackpad flick clears the window before the 90ms settle ever fires ("the scroll jack doesn't work on desktop"); phone only hid this because its finale runway is deeper. The band is self-bounding — `#creators` starts exactly at this section's bottom (both edges measured at 4511), so `rect.bottom` *is* the next section's top: above `DEAD` you have not arrived, at or below it you are already inside (a sticky-pinned creators reads `top: 0`), and a fling that overshoots the whole section leaves it negative. The end guard inside the engaged path stays for the case where you leave the stack while the story is still on the line — and its `segDir === 1` gate lives IN the condition, not as an early return, so a non-downward run falls through to the plain tidy (with `best < 0` that pulls UP onto the stack, i.e. WITH the gesture); the gate itself shipped MISSING once — the comment promised it, an upward run landing short of the pledge got jacked back down against the user ("the scroll jack glitches sometimes"). Verified live at `rect.bottom = 220`: downward run → glide starts, upward run → nothing, already-inside → nothing. **Two momentum-tail rules keep the jack alive on trackpads** (the other half of that report): (1) the seam-first test blocks only `segDir === -1` — direction UNKNOWN resumes the jack, because a tail tick that kills the glide mid-flight also REBASES the run to 0, and the old `!== 1` gate then stranded the page half-way into the seam; (2) end-carry glides (`glideBy(…, seam=true)`: the creators seam AND the hero exit) ignore SAME-direction wheel ticks in `onGesture` — they are the fling's own tail, and the glide is already finishing that gesture — while opposite-direction ticks and any touchmove still kill it like every other gesture. The PHONE still frees the upward one. The DESKTOP top is the opposite (owner: "when I move up it shouldn't go up" — above step one there is only the raw hero→story seam): an uncommitted up-drift snaps BACK onto step one, and a committed up-flick (the same `0.12·H` bar as the advance; a slow continuous crawl accumulates run travel and commits too, so there is no trap) glides all the way onto the hero (`best = rect.top − H`, clamped at doc top, on the advance carry ramp). Interior steps still snap both directions.
  Both are reached only off a real gesture, and both were rebuilt after repeated reports of the page moving by itself — the causes were `scroll`-event arming and the idle timer, not the behaviours themselves. Fix the trigger, not the feature.
- **GSAP is gone.** Not in `package.json`, not in the lockfile, not imported anywhere. Motion runs on native primitives (a deliberate user decision overriding DNA §6). [lib/motion.ts](lib/motion.ts) is the shared kit: `EASE` (cubic-beziers matching the old GSAP curves — power1/2/3/4.out, in2/inOut2/inOut3, back.out tiers), `easeFn` (the same curves as plain functions for rAF loops), `splitWords` (SplitText word-mask parity incl. the 0.18em descender allowance), `onceInView` (ScrollTrigger `once` parity via IntersectionObserver), `park` (gsap `autoAlpha: 0` parity), and `playFrom`/`playTo` (Web Animations API with gsap-style `.from()` immediate-render parking and freeze-on-interrupt retargeting). Continuous loops (creators wheel, Evan) drive rAF directly. The vendored GSAP builds and the `lib/proovd-motion.js` stub have been deleted; remaining GSAP mentions are comments explaining what a helper replaces. Don't reintroduce the library or the stub.
- **Section conventions are unchanged:** every section is a `"use client"` component animating inside `useLayoutEffect`, with cleanup that cancels its animations/observers and clears its inline styles, an early bail-out under `prefers-reduced-motion: reduce` (navbar excepted — it only skips the logo flight), a `Promise.race([document.fonts.ready, 600ms])` before word splits, and fail-open try/catch so a throwing motion layer never leaves content hidden.
- **[components/evan-section.tsx](components/evan-section.tsx)** is a faithful port of a user-supplied reference scroll story ("Proovd Scroll Storyyy") with its own self-contained rAF engine, split across four effects (E1 story engine, E2 mode re-paint, E3 corner-peel, E4 opening statement). Scroll-chasing exponential smoothing (`k = 1 − e^(−dt·7)`) plus CSS transitions drive its text/media choreography; THREE.js (dynamically imported, with raw GLSL in `VERT`/`FRAG`) renders the corner-peel page transition, and any failure — no WebGL2, image error, chunk error — silently falls back to the CSS scene crossfade. It scopes a fluid unit `--u` to the section (uniform zoom of a 1440×800 reference — **never** applied to the page root). Don't let its scroll-chasing patterns leak into other sections.
  - **The exported `EvanSection` is a thin posture gate; the engine lives in `EvanStory`.** Both postures are 4 beats with no "Evan…" kicker and the same pledge+CTA finale now, but they are still DIFFERENT-shaped trees — phone bodies are word-masked span forests; desktop bodies are plain text blocks — so it can't be a CSS restyle of one tree. `EvanSection` decides `posture` from `matchMedia("(max-width: 700px)")` (SSR + first client render are always `"desktop"`, so hydration matches; the effect then flips) and renders `<EvanStory key={posture}>`. **The `key` is load-bearing:** posture is a change of node structure, and the engine's E1/E3 capture the step/scene/tick nodes once at mount with `[]`-style deps — so a posture change must REMOUNT the story (fresh DOM, effects re-init through their normal mount) rather than mutate it in place. Within a mounted instance posture is fixed, so mode-switching (idea↔product) stays same-count (4↔4) and E1/E3 never re-run. The copy lives in ONE place (owner: "make it the same copy in the phone"): `IDEA_COPY`/`PRODUCT_COPY` are plain strings — no `<mark>` anywhere, and the `--mk` sweep is deleted from engine + stylesheet — and `tellWith(copy, photos)` derives all four step tables, pairing the copy with `LAPTOP_PHOTOS` or `PHONE_PHOTOS` — except PRODUCT, whose tables swap only the FIRST subject for `Product_evan_desktop/mobile.webp` (owner: "when i select product the first pic should be the evan product pic"); the other three files are shared. The flip still needs no pre-warm loop: E3 loads the UNION of both modes' srcs (`UNIQUE`) before building the renderer, so the product texture and the browser cache are both warm on every path, and the panel aspect + cover-crop are measured per image (the product desktop cut is 1225×1165 vs idea's 1115×1165; the mobile cuts are identical at 1118×618). Tick counts derive from the live count (`slides.length`); the peel's z-order from `activeSrcs.length`. **Every sheet peels from the SAME corner on BOTH postures** (`PEELS` is a single bottom-right entry, per the owner), and the curl **rolls past the stamp edge**: `.walkMedia` has NO `overflow: hidden` and `.peelMount` keeps `-15%` inset on phone (a measured GPU budget) but `-45%` at ≥901px, so the desktop curl rolls clear of the panel instead of being cut at an invisible boundary ("peel off, not masked" — the roll cylinder extends ~35% of the panel height past the corner); `.section` has `overflow-x: clip` at base (NOT `hidden`, which would create a scroll container and break the sticky media pin) so any spill leaves the screen instead of causing sideways page pan. **Desktop retires its chrome per-frame in `update()`** — the sticky stamp + fixed bar fade over `max(top-edge, bottom-edge, closing-screen)` distance (200px ramps; the closer term mirrors the phone's pledge-screen retire) so neither ever rides out of the story with the page; derived, never latched, cleared in E1 teardown. The navbar logo is deliberately a bit bigger on both postures (`navbar.module.css`: base `clamp(1.75rem, 2.6vw, 2.875rem)`, ≤700px `2.125rem` with 1rem vertical padding); everything that depends on nav size measures it live, so nothing else moves with it. Photos show at their NATURAL aspect on both postures (the panel takes the FIRST photo's ratio — 825/862 on desktop, 380/210 phone — and the others cover-crop in). Phone specifics, all off the same posture flag:

The jack's remaining frames become no-ops and its `SLIP` check — comparing `window.scrollY`, frozen at 0 under the pin, against where it expects to be — aborts it cleanly. **The glide only ever runs FORWARD** (`gap > 1`): arriving from below puts the section top above the viewport, and gliding then would drag the reader back through a section they just left. `pin()` also stands down if `body.style.position` is already `fixed` (another owner holds the page; stacking a second pin would read `scrollY` as 0 and restore the document top). Released by whichever comes first: the arc landing (`p >= 1` / `endIntro()`, which also covers a finger taking the drum over mid-spin), the `BLANK + INTRO + 400ms` timer backstop (a backgrounded tab suspends rAF but not `setTimeout`), or unmount — **a body left `position: fixed` freezes the whole site**, so every path must reach `release()`.

Two things follow from moving the start: `armed` (desktop) / `started` (phone) — which gate `play()` — are set at the *real* start rather than at the trigger, or the wheel would step through its normal glide/dwell behind the parked opacity during the blank; and `holdScroll` fires `onSettled` even when it stands down (body already `fixed`), or a one-off collision would cost the section its entire opening. `triggered` is the new once-guard, and the blank timer is cleared on unmount alongside the hold.

It is NOT padding on the panel: an absolutely positioned child's containing block is the padding *box*, which includes the padding area, so `inset: 0` covered it and the frame measured **0px** wide. **The fall is masked to the panel** (`overflow: hidden` on `.stack`, owner: "i want them masked inside this black square") — a card tipping forward grows toward the viewer and used to swing clear of the frame; measured mid-fall at −66°, it spilled 64px past each side and 199px above. ## Postures: phone, tablet-blocked, laptop

Three ranges, and the middle one is deliberately not designed:

- **Phone (≤700px)** — runs the same intro as desktop on its own portrait clip. `CLIP.phone` is `mobile-video.mp4` (1080×1920, 1.37s); `CLIP.desktop` is the 16:9 one. The gate ships the `<video>` with **no `src`** and sets it from `matchMedia` in the effect, so only one file is ever fetched — a `src` in the JSX had the preload scanner pull the desktop clip on phones too, where `cover` reduced it to a strip of its own middle. Phones snapshot their clip's last frame like desktop, so the phone dissolve override is gone and `Hero_mobile.webp` is fallback-only. **The Evan story is a phone-specific rebuild** (see the `EvanSection` posture-gate note under Motion): a 4-beat cut on a flat `#001407` surface, no kicker, new stamped photos (`*_new*.png`), ending on a pledge sticker + "Start campaign". The idea/product theme flip is visually disabled on EVERY posture now — phone pins `#001407` in the ≤700px block, desktop's base palette IS the navbar's `#011E0B` — so the pick only swaps copy. The one exemption is the **opening "This is Evan…" statement, which stays white on phone too** — deliberate, per the owner; `.statementWrap` pins its own `--ev-bg`/`--ev-ink` so the mobile dark palette doesn't reach it. The photo-swell routine there is unchanged. **The creators section is a phone-specific rebuild too** — the guide-ported 3D drum carousel (see its bullet under Motion), reached by the Evan magnet's phone seam-jack.
- **Unsupported (701–1023px wide, *or* ≥701px with `pointer: coarse`, *or* ≥701px and under 600px tall)** — [components/tablet-block.tsx](components/tablet-block.tsx) covers the page at `z-index: 2000`. Three queries because none suffices alone: `pointer: coarse` catches every iPad in both orientations (including the 12.9" landscape at 1366px, which no width rule would see as a tablet); the width range catches tablets reporting a fine pointer plus narrow desktop windows; and the **height** rule catches short windows, where a display headline and the CTA cannot both clear the fold at laptop type sizes no matter how the padding is tuned (measured: at 1280 wide the hero wanted ~737px). It's a server-rendered, `display: none` element — no JS, no hydration, painted on the first frame. The same queries are mirrored in `styles/globals.css` (holds the page still underneath) and in `intro-gate.tsx`'s `TABLET_QUERY` (so the intro doesn't buffer 1.6 MB behind an opaque cover). **Change one, change all three.**
- **Laptop (≥1024px)** — the hero has two hard guarantees at every size, enforced by measured geometry in `hero.module.css`:
  - *His face is never cropped.* The 16:9 photo is anchored `right top`. Right, because the subject sits in the right half, so centre-anchoring cropped into his face once the viewport went narrower than 16:9. Top, because his hair starts **0.9%** down the frame while there's ~15% of dead room below his beard — centre split the vertical crop evenly and shaved his hair on anything wider than 16:9.
  - *The type never reaches him.* `--subject-x: 0.46` is the fraction of the frame width where his silhouette begins (**measured**: hair texture edge ≈ 0.47, lit face ≈ 0.57). The headline column is capped at `100vw − max(100vw, 177.78svh) × var(--subject-x)` minus the gutter and a clear gap, and the font-size is divided out of that column so a long word can't outgrow it.

  - *The CTA never falls below the fold* (DNA §9). The hero's vertical rhythm is width-derived by default, which on a short window spends more on padding than there is room for; `padding-top`/`padding-bottom`/`.start`'s `margin-top` and the headline's font-size are each capped against viewport height as well. All four caps are inert at normal aspects.

  Re-cutting the clip or swapping the still means re-measuring `--subject-x` and the 0.852 bottom bound. Verified 1024×600 → 2560×1300: clearance 26–51px, face whole on both axes, CTA above the fold by 32–107px throughout. Past ~2.09 aspect something must clip whatever we do; the bottom of a beard is the cheapest thing to lose.

## Other conventions

- Images are plain `<img>` tags serving pre-optimized WebP from `public/assets/` — not `next/image`, because the FLIP flights `cloneNode` and measure these exact nodes.
- SEO reads from one place: [lib/site-config.ts](lib/site-config.ts) drives the Metadata API in `app/layout.tsx`, `app/robots.ts` (with an explicit AI-crawler allow-list), and `app/sitemap.ts`. `defaultTitle` is `"PROOVD"` — the tab text, all-caps per the owner; the e2e asserts it straight from the config. The favicon is the owner's `assets/Proovd-favicon.svg` with `/favicon.png` (rasterized from the same SVG) as the fallback for engines that can't take SVG icons — `app/favicon.ico` was DELETED deliberately: it was the stock create-next-app icon and Next auto-injects any file at that path ahead of `metadata.icons`, which handed Safari the Next.js logo. `app/page.tsx` builds one JSON-LD `@graph` (Organization + WebSite + FAQPage) via [lib/json-ld.tsx](lib/json-ld.tsx); its FAQ content comes from [lib/faqs.ts](lib/faqs.ts), the single source shared by that server-rendered schema and the client `FaqSection`. [public/llms.txt](public/llms.txt) is a hand-maintained GEO surface — keep it and `siteConfig` in sync when the facts change. `siteConfig.ogImage` points at `/og.png`, which **does not exist yet**.
- Analytics (`components/analytics.tsx` — Microsoft Clarity + self-hosted Umami) renders only when `NODE_ENV === "production"` **and** the relevant `NEXT_PUBLIC_*` vars are set — development stays free of third-party scripts.
- Biome: double quotes, 2-space indent, 80-char lines; `docs/`, `public/`, and `styles/` are excluded from it.
- Path alias `@/*` maps to the repo root (also aliased in `vitest.config.ts`).
- `README.md`, `DEPLOY.md`, `SEO-AUDIT.md`, and `SEO-CHANGES.md` are point-in-time records that **predate the GSAP-free rewrite**.
