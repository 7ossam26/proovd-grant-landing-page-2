npm only. Dev server: `npm run dev` (http://localhost:3000) — also wired as the `dev` entry in `.claude/launch.json`.

| Command | Notes |

| `npm run start` | Serve the production build on port 3000 (run `build` first) |
| `npm run lint` | Biome check (lint + format diagnostics) — no ESLint/Prettier |

Add a stub there rather than guarding component code for the test environment.

Both suites assert exact copy: the hero `<h1>` string, `siteConfig.defaultTitle`/`.description`, the section ids, and an `FAQPage` in the JSON-LD. Changing that copy or `site-config.ts` means updating `tests/smoke.test.tsx` and `e2e/smoke.spec.ts` in the same pass.

## What this is

Single-page marketing site for **Proovd** (Next.js 16 App Router + TypeScript, Turbopack). One route: [app/page.tsx](app/page.tsx) renders `IntroGate`, then `<main>` composing the sections in order (Hero, Navbar, Evan, Creators, Risk, Days, Guides, Pricing, FAQ) with `HoverFX` last — most sections are one viewport tall; Evan is a multi-viewport scroll track with a sticky stage. React/Next are the only runtime dependencies — `three` was removed with the corner-peel.

**[components/intro-gate.tsx](components/intro-gate.tsx) owns the first ~4.5s of the page** — a full-screen `z-index: 1000` intro that runs, then lifts. One `data-phase` state machine drives it: `loading → choosing → picked → sealing → playing → done → gone`. All choreography is CSS keyed off that attribute; the component only advances the phase and drives the `<video>`s.

- **Loading** → before the buttons (owner): a 0→100% count (rAF writing `textContent`, `LOAD_MS 1800` + `LOAD_TAIL 250`, with a timer backstop since a hidden tab suspends rAF) under `crank-load.mp4` looping above it (~750 KB, gated on Save-Data/tablet/codec — its absence just hides the clip, the count runs regardless). **The media is armed at PARSE time, not hydration**: `MEDIA_KICK`, an inline script in `app/page.tsx` right after `<IntroGate />`, sets both video srcs behind the same reduced-motion/Save-Data/tablet/codec/posture gates — measured live, hydration lands at ~5.5s under Fast 3G and a fetch that starts only then loses every race the intro runs. The gate's effect re-arms ONLY if the kick didn't run (`currentSrc` guard — re-assigning the same src restarts the download), and its deny paths (`!allowClip`, `hideCrank`) ABORT a kick-armed fetch (removeAttribute+load), covering a rotation into the tablet band between parse and hydration. KEEP THE KICK'S QUERIES IN SYNC with `TABLET_QUERY`/`PHONE_QUERY`/`canPlayMp4`. **The count parks at 99% until the crank's first frame** (`loadeddata`, capped at `LOAD_CRANK_WAIT 2500` past the count) — the shipped fixed count reached 100% with the 768 KB clip still headerless on every throttled probe ("the loading crank video doesn't show up"). Deliberately NOT the reverted c7fdd4d design: that keyed on `canplaythrough` (WebKit never fires it — stalled iPhones at 90% for its full 8s cap) plus window `load`; `loadeddata` fired on every probed engine. `.loader` and `.choices` share grid cell `1/1`; the tiles hold layout underneath at `visibility: hidden` so the swap is an in-place reveal. Reduced motion skips straight to `choosing`. The StrictMode-unmount claim-release now covers `loading` OR `choosing` — `finishIntro()` from there would settle the intro for good and the remount would land on `gone`.
- **Pick** → the tile strobes 3 × 0.12s while the other shuts (`max-width`/padding/border → 0, its grid row `1fr → 0fr`, row-gap → 0, so the survivor glides to centre). The row collapse is the flexible-track trick `faq-section.module.css` uses to open an answer, run in reverse.
- **Sealing** → the picked tile takes that identical exit, one beat later.
- **Playing** → a muted 0.97s stinger (`public/assets/desktop-video.mp4`, ~560 KB after the owner's re-encode), `object-fit: cover`.
- **Done/gone** → the clip is cut away onto its own snapshotted last frame, and `<Hero />` runs its normal reveal.

Rules that are load-bearing here — breaking any of them re-opens a bug that was already found and fixed:

- **`go()` is monotonic.** `finishIntro()` can fire from *outside* the sequence (Escape, the module deadline), which leaves the pick chain queued. A later `go("sealing")` would drag the opaque overlay back over a revealed hero with nothing left to remove it — the `whenIntroDone()` handler runs exactly once. That handler therefore also tears the sequence down (`ended`, `clearTimers`, `detachVideo`) *before* advancing, and the exit timer is deliberately kept out of the array `finish()` clears.
- **The hero backdrop is the clip's own last frame.** On the desktop clip path `snapshotFrame()` draws the `<video>` into a `<canvas>` and puts it in `.bg` — pixel-identical by construction, so there is nothing to keep in sync and no separate still is fetched at all. Measured: ~1–4 ms, canvas is not tainted (same-origin file). **Do not encode it first** — `toBlob('image/webp')` on a 1080p frame measured 414 ms of main-thread work here, for a `<canvas>` that was already paintable. A held frame costs about the same GPU memory as the decoded still it replaces (~8 MB either way), so this is a straight saving of the still's bytes.
- **There is NO fallback still any more.** The owner deleted the hero art outright in the webp sweep (`new_hero_desktop.*` and `Hero_mobile.webp` are gone; `HERO_ART` was removed with them and `loadStill()` is a kept-for-sequencing no-op). On every path where no clip frame can exist — reduced motion, Save-Data, refused autoplay, unplayable codec, dead file, JS off — the hero stands on `.hero`'s own `background-color` surface, and the gate always *dissolves* there: `heroDecodedRef` can only be set by a real snapshot now, so `data-cut="hard"` is unreachable without a frame.
- **`data-cut="hard"` requires all three of**: a frame painted, `heroDecodedRef` (else the cut lands on `.hero`'s green `background-color` against the navy — a colour flash), and `cutOnEndedRef` (the `timeupdate` net can fire 60ms early, and the final frames are where residual motion lives). Anything less dissolves.
- **`.video` is sized from `--crop-w/h/y`**, published by a `ResizeObserver` on `section[aria-label="Proovd"]`. `cover` resolves against the box it paints into, and `.hero` is `min-height: 100svh` — taller than the viewport when content overflows — so a viewport-sized clip would zoom/shift at the cut instead of matching.
- **The clip is gated on `saveData` only, never `effectiveType`.** That was measured misfiring: Chrome reports `2g`/`slow-2g` while its estimate is cold, denying the clip on localhost. Slow connections are handled by the measured `T.buffer` grace instead.
- **Playback starts at `PLAYABLE` (HAVE_FUTURE_DATA / `canplay`), not HAVE_ENOUGH_DATA/`canplaythrough`.** The old bar dropped fully-downloaded clips on engines that never report it — WebKit 8/8 probed loads, Firefox 1/4 — which is a big slice of why iPhones always landed on the plain hero. `T.buffer` still caps the wait and `T.video` still ceilings a stall mid-play ("drop rather than stutter" survives as the backstop). Known accepted tradeoff pending an owner decision: a clip that stalls mid-play now snapshots its CURRENT frame at the `T.video` cut (better than the bare color, not the true last frame); the `intro-end` beacon reports `t`/`d` so field data can settle the policy. An EXTERNAL finish (Escape, the 7s deadline) now snapshots too when a frame was painted, instead of discarding it.
- **[lib/intro.ts](lib/intro.ts) exposes TWO signals, and conflating them is a bug that has already happened once.** `whenIntroDone()` = "the hero may un-park"; `whenIntroDismissed()` = "the gate may leave". The idle backstop resolves only the first. When the gate hid itself off the *same* promise, it evaporated on its own ~15s after load in front of anyone still reading the two options, so their click landed on nothing — which presents as "the second tile doesn't work". Only a real end (clip finished, genuine failure, Escape, post-pick deadline, unmount mid-sequence) may dismiss the gate. `introSettled()` reports *dismissed*, not *settled*, for the same reason.
- **[lib/intro.ts](lib/intro.ts) is the handoff** — promises that can only resolve. It owns every backstop so no consumer can forget one: a claim grace (gate present but silent), a 7s sequence deadline (armed by the pick), and a 20s **idle** backstop for "nobody ever clicks", which the pick *cancels* — otherwise a visitor who reads the options slowly would have their hero reveal spent behind the still-opaque gate. `whenIntroDone()` also answers "is there even a gate?" via the server-rendered `data-intro-gate` marker, so deleting `<IntroGate />` from `page.tsx` resolves it instantly rather than parking the hero on a timer.
- **The statement photo swaps main→smiling by stacking, not `src`.** Two `<img>` (`[data-ev-photo]` + `[data-ev-photo-smiling]`) sit absolutely inside `.photoMask`, smiling pre-decoded at `opacity:0`; the cut flips its opacity to 1. Re-setting `src` on a live `<img>` flashes during decode/repaint even when cached — that was the "pic flickers" bug. On phone the photo window GROWS in layout and holds big (see the Evan notes below); desktop keeps the straight settle-then-smile. At the handoff the photo fades up-and-out with the words on BOTH postures — there is no kicker avatar anywhere any more, so the old `flyToAvatar` flight is gone.
- **`history.scrollRestoration = "manual"`** (set in IntroGate) + `scrollTo(0,0)`: every load starts at the top, never the restored position — so the intro gate is never lifted onto a mid-page position the visitor did not choose. (It was originally there because the hero→Evan scroll-jack assumed you began on the hero; that jack is gone, but starting a gated page-view at the top is still the right behaviour, and `e2e/intro-resilience.spec.ts` asserts it.)
- Reduced motion skips the video entirely and lands straight on the hero. `<noscript>` + `@media (scripting: none)` hide the gate outright — with JS off it is a modal with no way out.

The pick is still sticky and navigates nowhere (`TODO(destination)`); both tiles run the same intro. It **is** load-bearing in one way, though: the gate records it via `setIntroChoice()`, and the Evan story reads it through `getIntroChoice()` once the intro resolves, to decide whether to tell `IDEA_STEPS` or `PRODUCT_STEPS`. Evan used to carry its own fixed segmented toggle asking the identical question with the identical two labels — that's gone, so the gate is now the only place the question is asked and `PRODUCT_STEPS` is reachable only through it. Nobody choosing (idle backstop, reduced motion, no gate) leaves the story on `idea`.

Deployed as a Docker standalone image (multi-stage `node:22-alpine`, non-root) via Dokploy on push to `main` (see DEPLOY.md). Config is env-driven and **inlined at build time** — Dokploy passes each value as a build arg (`Dockerfile` ARG/ENV pairs), so a var set only at runtime has no effect. The set: `NEXT_PUBLIC_SITE_URL` (canonical origin; code falls back to `https://proovd.co`), `NEXT_PUBLIC_CLARITY_PROJECT_ID`, `NEXT_PUBLIC_UMAMI_SRC` + `NEXT_PUBLIC_UMAMI_WEBSITE_ID`, and `GOOGLE_SITE_VERIFICATION` (the one non-`NEXT_PUBLIC_` var, read server-side in the metadata). All optional — each feature stays off until its var is present.

## Design system — three layers

1. **Decision layer:** `docs/design-system/Proovd DNA.md` — the brand/UX/motion spec. The `§` numbers in code comments (e.g. "§6.4") refer to its sections. Read it before building or restyling any UI; it contains hard rules (color pairings, "nothing teleports", fail-loud font/motion checks, no shadows/gradients, sharp radii). Its GSAP-only motion rule (§6, §6.7) is deliberately overridden in this codebase — see Motion below.
2. **Value layer:** [styles/proovd.css](styles/proovd.css) — tokens, section modes, element identity, and the Satoshi `@font-face`. **Never edit or format this file** (it's excluded from Biome); it is replaced wholesale from `docs/design-system/proovd.css`, which is currently byte-identical. The intended contract: components pick a section mode class (`.mode-none` / `.mode-dark` / `.mode-light` / `.mode-drawer`) and read semantic slot vars (`--mode-title`, `--mode-body`, `--btn1-*`, …) rather than hex. In practice these landing sections read the raw **token vars** directly (`--brand`, `--dark`, `--sp-*`, `--fs-*`) — the `.mode-*` slot system and the `.btn`/`.card`/`.sticker` element classes are essentially unused here — and a few section-local palettes are hardcoded (the creator card sheet in `creators-section.tsx`, the `#011E0B` shared by navbar/risk/days/Evan-product-mode). So don't expect to find `.mode-dark` on a section; look for the token vars in its `*.module.css`.
3. **Component layer:** CSS Modules co-located with each component (`components/*.module.css`). No Tailwind, no CSS-in-JS, no UI libraries. [styles/globals.css](styles/globals.css) holds only page-level overrides (hidden scrollbars, the `data-hover="underline"` ::after scaffolding).

Fonts: Satoshi is load-bearing, self-hosted in `styles/fonts/`. `app/layout.tsx` imports the woff2 for its hashed URL (ambient decl in `types/assets.d.ts`) and `preload()`s it so the preload always matches the `@font-face` request. The DNA's fail-loud `document.fonts.check` notice (§3) is **not** implemented.

## Motion & scroll architecture

- **Native scroll is the ONLY source of truth. Nothing on this site writes the page position any more.** The chain is `native browser scroll → section progress → story position → rendered visual state`, and it runs one way. No section calls `scrollTo`/`scrollBy`, preventDefaults a wheel or touch event, pins `<body>`, locks body overflow, or keeps a virtual scroll. The previous architecture did all of those — a body pin with a `body.style.top` glide (`holdScroll`), the Evan story's `holdInput()` + `settleToTop()`, a hero→Evan scroll-jack, and a "whisper magnet" that snapped onto the nearest beat — and every one of them was a second opinion about where the visitor was. When two opinions disagreed you got the shipped bug list: the page frozen, scroll taken away, scenes stuck after a fling, reverse not restoring, the scrollbar showing the wrong scene, a body left pinned. Deleting the other opinions deleted the class of bug. **Do not reintroduce a scroll writer.** The two remaining `body.overflow` locks belong to genuine MODALS (the intro gate, the navbar's phone sheet), which is standard behaviour and not part of the story. No CSS scroll-snap. Everything reads position passively (rAF-coalesced passive listeners).
- **`holdScroll` in [lib/motion.ts](lib/motion.ts) is now a no-op compatibility shim.** It kept its signature so creators / risk / days / guides did not have to change, but it touches nothing: it fires `onSettled` on the next microtask and returns a cancel fn. Those four sections therefore still play their entrances on arrival (`onceInView`), just without the page being taken away first. `VSCROLL_EVENT`, `pokeVScroll` and `hasLiveHold` are deleted — they existed only to broadcast a virtual position that no longer exists.
- **[lib/scroll-story.ts](lib/scroll-story.ts) is the story's arithmetic, and it is pure.** `trackProgress`, `storyPositionAt`, `activeSceneIndex`, `sceneVisualAt`, `curtainPanelProgress`, `rampBetween`, `clamp01`. No DOM, no window, no state, no timers — which is what makes the behaviour testable without a browser and, more importantly, TOTAL: hand it any progress in any order and it returns the right frame, so a scrollbar drag and a reverse are not special cases. `clamp01` deliberately folds NaN and `-0` to `+0` (a NaN progress would otherwise reach the DOM as `opacity: NaN`, which browsers drop, stranding a scene at whatever it last was).
- **GSAP is gone.** Not in `package.json`, not in the lockfile, not imported anywhere. Motion runs on native primitives (a deliberate user decision overriding DNA §6). [lib/motion.ts](lib/motion.ts) is the shared kit: `EASE` (cubic-beziers matching the old GSAP curves — power1/2/3/4.out, in2/inOut2/inOut3, back.out tiers), `easeFn` (the same curves as plain functions for rAF loops), `splitWords` (SplitText word-mask parity incl. the 0.18em descender allowance), `onceInView` (ScrollTrigger `once` parity via IntersectionObserver), `park` (gsap `autoAlpha: 0` parity), and `playFrom`/`playTo` (Web Animations API with gsap-style `.from()` immediate-render parking and freeze-on-interrupt retargeting). Continuous loops (creators wheel, Evan) drive rAF directly. The vendored GSAP builds and the `lib/proovd-motion.js` stub have been deleted; remaining GSAP mentions are comments explaining what a helper replaces. Don't reintroduce the library or the stub.
- **Section conventions are unchanged:** every section is a `"use client"` component animating inside `useLayoutEffect`, with cleanup that cancels its animations/observers and clears its inline styles, an early bail-out under `prefers-reduced-motion: reduce` (navbar excepted — it only skips the logo flight), a `Promise.race([document.fonts.ready, 600ms])` before word splits, and fail-open try/catch so a throwing motion layer never leaves content hidden.
- **[components/evan-section.tsx](components/evan-section.tsx) is a tall scroll track with a sticky stage, and one controller.** The whole section is ~500 lines now (it was 2,853) and holds exactly one piece of mutable state: the cached track/stage heights. Structure: `.track` supplies the scroll distance (`100svh + 5 × --scene-span`), `.stage` is `position: sticky; top: 0; height: 100dvh` and pins for exactly that distance, and SIX scenes sit stacked inside it — scene 0 the opening statement, 1–4 the beats, 5 the finale. **DOM order IS the scene index.** One `useLayoutEffect` binds one update cycle: read the track's `rect.top` (the only per-frame layout read), compute progress → story position → active scene, then write. Scroll is a passive listener coalesced through `requestAnimationFrame`; geometry is re-measured on `resize`, `orientationchange`, `visibilitychange` and a `ResizeObserver` on both track and stage, never per frame.
  - **Every visual value is derived from the scene's signed distance** (`storyPosition − sceneIndex`), so scrolling back up runs everything backwards for free — there is no separate reverse path, and no "forward" and "reverse" sequences to keep in step. Copy opacity uses a sharp smoothstep falloff (only one headline is ever legible); media opacity is LINEAR so a crossfading pair always sums to ~1 and the panel never dips mid-swap. `visible` at `|d| < 1`, `interactive` at `|d| < 0.5` — that half-beat partition is what guarantees no invisible scene can sit over a button and eat the click.
  - **Exactly one scene carries `data-active`, and the section carries `data-active-scene`.** The active index is `Math.round(storyPosition)`, which flips at the same midpoint the crossfade hands over — so the marker and the scene your eye calls dominant cannot disagree. (They used to. That was the "visual scene and active scene disagree" bug.)
  - **The opening statement and the curtain are progress-driven, not played.** The white surface is five `.curtainPanel`s whose lift is `curtainPanelProgress(ramp(distance, 0.26, 0.86), i)` — the stagger is folded into the VALUE, not into a `transition-delay`, which is the only way dragging the scrollbar backwards puts every panel back where it was. The curtain is never unmounted. The neutral→smiling photo swap is a plain opacity crossfade between two identically-sized stacked `<img>`s over `ramp(distance, 0.06, 0.34)`, so it cannot shift layout.
  - **The progress bar belongs to the STAGE, not the viewport.** It is absolutely positioned at the stage's bottom, so it arrives and leaves with the sticky stage and never needs to be told which section owns the screen. The old one was `position: fixed` and had to be gated per frame against the viewport centre.
  - **Progressive enhancement is the fallback strategy for all four failure modes at once.** The markup is a plain document — six sections in normal flow, every image and word readable — and the controller sets `data-enhanced="true"` only after it binds. Only that attribute turns on the sticky presentation (`.section[data-enhanced="true"] …` in the stylesheet). So no-JS, a failed hydration, a throw inside the controller, and `prefers-reduced-motion` all land on the same readable document with no separate code path. Reduced motion is read in a `useState` INITIALIZER, not an effect, so such a visitor never sees even one painted frame of the sticky layout.
  - **Posture is the browser's job now.** The old `EvanSection` posture gate — `matchMedia`, a `key={posture}` remount, and two entirely separate component trees — is gone. There is ONE tree; `<picture><source media="(max-width: 700px)">` swaps the phone/desktop image files, and CSS handles the single-column phone layout. No resize listener swaps a URL any more.
  - **THREE.js is gone**, and with it the corner-peel, the GLSL, the WebGL context-loss recovery, the texture cache and the `alive`-check dance around the dynamic import. The transition it bought is now an opacity crossfade. `three` and `@types/three` were removed from `package.json` after confirming no import remained — that is ~725 KB raw / ~182 KB gzip of JavaScript deleted.
  - `data-track` / `data-stage` are attributes rather than hashed CSS-module class names specifically so [e2e/evan-scroll.spec.ts](e2e/evan-scroll.spec.ts) can compute the exact scroll offset of any progress value.
- **The navbar reads `window.scrollY`, full stop.** It used to read a "virtual" position (`-body.top`) because arrival holds pinned `<body>` and froze the real `scrollY` at 0, and it subscribed to a private `VSCROLL_EVENT` channel because a pinned body emits no `scroll` events. Nothing pins the body any more, so both are deleted and the bar is a plain rAF-throttled passive `scroll` reader again (plus `resize`, which moves the `#days` boundary without scrolling). The Evan statement no longer needs `z-index: 950` to outrank the bar either — it is ordinary content inside a sticky stage, and the bar sits over it like it does over every other section.
- **Cross-component wiring is DOM-based, not props:** the hero logo flies into the navbar via a manual FLIP — a `[data-hero-logo]` clone tweened (translate+scale, WAAPI) onto the measured `[data-nav-logo]` rect; navbar goes transparent over `#days`; Evan measures the rendered `nav[aria-label="Main"]` for its sticky offsets. Every CTA and nav link points at the real app (`siteConfig.founderUrl` / `affiliateUrl`), never at a section anchor — the section ids (`#idea`, `#creators`, `#risk`, `#days`, `#pricing`, `#faq`) exist for the scroll machinery and the smoke test, not for navigation.
- **Section stacking is a curtain, not a transition:** `creators-section` goes `position: sticky` above 900px and the following sections ride over it on `z-index` (risk 20, days/pricing/faq 30). Changing a section's `z-index` or `min-height` breaks that pin.
- **[components/creators-section.tsx](components/creators-section.tsx) is the last posture gate on the site** (Evan's was removed in the scroll rebuild — see above — so this pattern now lives here alone): ≥701px renders `CreatorsDesktop` — the original vertical recycling wheel, untouched — and ≤700px renders `CreatorsCarousel`, a 1:1 port of the owner's animation guide (`proovd-section-carousel-mobile.html`, in their Downloads; the guide's tunables are kept verbatim in the engine). The carousel is a 3D drum: cards curve cylindrically across 20 facet `.slice`s (each a clipped window onto the same `--img`, stepped around a cylinder of radius `PHOTOW/ang`), side cards turn away/shrink (`ROT_DEG 46`, `SIDE_SCALE .62`), and the focused card — swapped to a single flat node (`isFlat`) — auto-opens its stat panel on a settle→`EXPAND 400`→`HOLD 1700`→`COLLAPSE 290`→advance cadence. Drag/flick spins it (pointer capture, spring `SPRING 195/DAMPING 25`, `DRAG_PX 130`), arrows step it, a click focuses. The entrance is an oversized tilted spin (`INTRO_SCALE 2.4`, `INTRO_FROM −7`, 1400ms) while headline/pitch/CTA rise on the guide's cadence (.92/1.12/1.26s, hint 1.85s) — keyed off `[data-in]` set by `onceInView(root, 70)` (NOT page load; it usually fires mid seam-jack, see the magnet ends). CONTENT is the site's, not the guide's: the same `CREATORS` table drives both trees (photos, handles, counts, niches, per-card `bg`/`fg` sheet colors, real platform logos — owner: don't change those). **The WORDS are single-sourced too, in `COPY`** (owner: "use the same copy from mobile to desktop") — the guide's headline "Creators do your marketing", the pitch, and "Start Campaign" → `founderUrl`, consumed by both trees so they can't drift the way the Evan story's did. Desktop's old brand-green eyebrow and its longer heading are gone with it (phone has no eyebrow); `.eyebrow` was deleted and `.pitch` added to `creators-section.module.css`. No test asserts these strings, but `e2e/smoke.spec.ts` requires exactly one `<h1>` on the page, so this heading must stay an `<h2>` on both postures.
- **The phone drum measures off PROBES, never off a card** (`[data-probe]` → `--photow`, `[data-probe-panel]` → `--panelw`; both `visibility: hidden`, so they are always laid out). `draw()` culls cards past `VISIBLE` with `display: none` and card 0 is culled by the very first frame, so the guide's `cards[0].querySelector('.panel-in').offsetWidth` read 0 on every re-measure and fell back to its hardcoded `146` — a number `clamp(130px, 39.4vw, 181px)` never takes, which is why it looked plausible. `.panelIn` is anchored RIGHT inside a `.panel` window of width `--pw` with `overflow: hidden`, so the shortfall clipped the panel's LEFT edge: measured 16px gone at 412 wide, taking the platform logo and the "Niche:" label with it, worse the wider the screen ("on some screen sizes the logo and niche get cutoff"). Both reads `Math.ceil` and keep the LAST GOOD value rather than degrading to a constant. `draw()` also reads a cached `stageW` — never `stage.clientWidth` per frame (the Evan E3 lesson).
- **Desktop has its own entrance** (owner: "an animation intro like this one but for the desktop version… bigger and in the middle then gets smaller to its original size and goes right"). The arc is parked at the entrance's own t=0 state before first paint — oversized (`INTRO_SCALE 2.4`), tilted (`-7deg`), spun `7` slots back, with its focal point translated onto the viewport centre — then `[data-in]` fades it up and 1400ms unwinds all four together, the spin resolving first. Load-bearing details: (1) **the trigger is the PIN** (`onceInView(root, 5)`), not the phone's 70% — the section is `sticky/top:0` and the wheel is `100svh`, so the arc's vertical centre coincides with the viewport centre only once pinned, which is what makes "in the middle" a pure horizontal translate; at 70% the whole entrance would play a viewport below the fold. (2) **`unfold` gates the focal unfold shut through the whip** — seven cards cross the ±10° window in one spin and would each pulse open/shut, a strobe; the phone forces `open = 0` for the same reason. It ramps back in over the last 28% so the focal card opens as the arc lands. (3) `transform-origin` is the focal point `(focalX, cy)`, so scale/rotate can't move it; `introDx` is cached in `measure()` off `root`'s rect + `offsetLeft` (never the transformed wheel's rect) and never read per frame. (4) The travel **overshoots ~5% past home on a `back.out(1.2)` and settles back RIGHT** — the arc's home is LEFT of centre (focal point 206px vs a 720 centre at 1440), and no transform-origin can swap the endpoints of a centre→home path, so a rightward FINAL motion can only come from the path. Landing it on the right would mean mirroring a layout built entirely around a left arc. ## Postures: phone, tablet-blocked, laptop

Three ranges, and the middle one is deliberately not designed:

- **Phone (≤700px)** — runs the same intro as desktop on its own portrait clip. `CLIP.phone` is `mobile-video.mp4` (1080×1920, 1.37s); `CLIP.desktop` is the 16:9 one. The gate ships the `<video>` with **no `src`** and sets it from `matchMedia` in the effect, so only one file is ever fetched — a `src` in the JSX had the preload scanner pull the desktop clip on phones too, where `cover` reduced it to a strip of its own middle. Phones snapshot their clip's last frame like desktop, so the phone dissolve override is gone and `Hero_mobile.webp` is fallback-only. **The Evan story is ONE tree on every posture now** — no posture gate, no remount. `<picture>` swaps the phone image files and CSS does the single-column layout; the phone surface stays `#001407`. The idea/product theme flip is visually disabled on EVERY posture now — phone pins `#001407` in the ≤700px block, desktop's base palette IS the navbar's `#011E0B` — so the pick only swaps copy. The one exemption is the **opening "This is Evan…" statement, which stays white on phone too** — deliberate, per the owner; `.statementWrap` pins its own `--ev-bg`/`--ev-ink` so the mobile dark palette doesn't reach it. The photo-swell routine there is unchanged. **The creators section is a phone-specific rebuild too** — the guide-ported 3D drum carousel (see its bullet under Motion), reached by the Evan magnet's phone seam-jack.
- **Unsupported (701–1023px wide, *or* ≥701px with `pointer: coarse`, *or* ≥701px and under 600px tall)** — [components/tablet-block.tsx](components/tablet-block.tsx) covers the page at `z-index: 2000`. Three queries because none suffices alone: `pointer: coarse` catches every iPad in both orientations (including the 12.9" landscape at 1366px, which no width rule would see as a tablet); the width range catches tablets reporting a fine pointer plus narrow desktop windows; and the **height** rule catches short windows, where a display headline and the CTA cannot both clear the fold at laptop type sizes no matter how the padding is tuned (measured: at 1280 wide the hero wanted ~737px). It's a server-rendered, `display: none` element — no JS, no hydration, painted on the first frame. The same queries are mirrored in `styles/globals.css` (holds the page still underneath) and in `intro-gate.tsx`'s `TABLET_QUERY` (so the intro doesn't buffer 1.6 MB behind an opaque cover). **Change one, change all three.**
- **Laptop (≥1024px)** — the hero has two hard guarantees at every size, enforced by measured geometry in `hero.module.css`:
  - *His face is never cropped.* The 16:9 photo is anchored `right top`. Right, because the subject sits in the right half, so centre-anchoring cropped into his face once the viewport went narrower than 16:9. Top, because his hair starts **0.9%** down the frame while there's ~15% of dead room below his beard — centre split the vertical crop evenly and shaved his hair on anything wider than 16:9.
  - *The type never reaches him.* `--subject-x: 0.46` is the fraction of the frame width where his silhouette begins (**measured**: hair texture edge ≈ 0.47, lit face ≈ 0.57). The headline column is capped at `100vw − max(100vw, 177.78svh) × var(--subject-x)` minus the gutter and a clear gap, and the font-size is divided out of that column so a long word can't outgrow it.

  - *The CTA never falls below the fold* (DNA §9). The hero's vertical rhythm is width-derived by default, which on a short window spends more on padding than there is room for; `padding-top`/`padding-bottom`/`.start`'s `margin-top` and the headline's font-size are each capped against viewport height as well. All four caps are inert at normal aspects.

  Re-cutting the clip or swapping the still means re-measuring `--subject-x` and the 0.852 bottom bound. Verified 1024×600 → 2560×1300: clearance 26–51px, face whole on both axes, CTA above the fold by 32–107px throughout. Past ~2.09 aspect something must clip whatever we do; the bottom of a beard is the cheapest thing to lose.
